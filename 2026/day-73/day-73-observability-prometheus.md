## Task 1 – Understanding Observability

### What is Observability?

Observability is the ability to understand the internal state of a system by analyzing the data it produces.

It helps DevOps engineers identify problems, investigate failures, and understand application behavior.

### Observability vs Traditional Monitoring

- **Monitoring:** Tells us when something is wrong through alerts, thresholds, and predefined conditions.
- **Observability:** Helps us understand why something is wrong by exploring metrics, logs, and traces.

### Three Pillars of Observability

**1. Metrics**

Metrics are numerical measurements collected over time.

Examples:
- CPU and memory utilization
- HTTP request count
- Application error rate
- Network traffic

Tools: Prometheus, Datadog, AWS CloudWatch.

**2. Logs**

Logs are timestamped records of events generated by applications and infrastructure.

Examples:
- Application errors
- Database connection failures
- Authentication events
- System activity

Tools: Loki, ELK Stack, Fluentd.

**3. Traces**

Traces track the journey of a request across multiple services in a distributed application.

They help identify slow services, bottlenecks, and failures.

Tools: OpenTelemetry, Jaeger, Zipkin.

### Why Do DevOps Engineers Need All Three?

- Metrics tell us WHAT is broken.
- Logs tell us WHY it broke.
- Traces tell us WHERE it broke.

Combining all three provides better visibility into application and infrastructure health.

### Observability Architecture

The planned architecture for the observability stack:

- Application metrics → Prometheus → Grafana Dashboards
- Application logs → Promtail → Loki → Grafana
- Application traces → OpenTelemetry Collector → Grafana / Debugging
- Host metrics → Node Exporter → Prometheus
- Docker metrics → cAdvisor → Prometheus

## Task 3 – Understanding Prometheus Concepts

Explored important Prometheus components and metric types.

### Scrape Targets

Scrape targets are endpoints from which Prometheus collects metrics at regular intervals.

Prometheus follows a pull-based monitoring model.

### Types of Metrics

**1. Counter**

A counter is a metric that only increases over time, except when reset.

Example: Total number of HTTP requests served by an application.

**2. Gauge**

A gauge represents a value that can increase or decrease.

Example: Current CPU utilization or available memory.

**3. Histogram**

A histogram measures the distribution of observations using configurable buckets.

Example: HTTP request duration.

**4. Summary**

A summary measures observations and calculates configurable quantiles on the application side.

Example: API response-time percentiles.

### Labels

Labels are key-value pairs used to add dimensions to metrics.

Example: HTTP request metrics can be categorized by method, status code, or endpoint.

### Time Series

A time series represents a sequence of metric values identified by a metric name and its label combinations.

### Prometheus UI Queries

Explored the following queries:

- `count({__name__=~".+"})` – Counts the matching time series.
- `process_resident_memory_bytes` – Displays Prometheus process memory usage.
- `prometheus_http_requests_total` – Displays total HTTP requests.
- `prometheus_http_requests_total{handler="/api/v1/query"}` – Filters requests by handler.

### Counter vs Gauge

| Counter | Gauge |
|---|---|
| Only increases | Can increase or decrease |
| Tracks cumulative values | Tracks current values |
| Example: Total requests | Example: Current memory usage |

## Task 4 – Learning PromQL Basics

PromQL (Prometheus Query Language) is used to query, filter, calculate, and analyze metrics stored in Prometheus.

### Important PromQL Concepts

**1. Instant Vector**

Returns the current value of a metric.

Query: `up`

**2. Range Vector**

Returns metric samples collected over a specified time range.

Query: `prometheus_http_requests_total[5m]`

**3. Rate Function**

Calculates the average per-second increase of a counter over a time window.

Query: `rate(prometheus_http_requests_total[5m])`

**4. Aggregation**

Combines metric values across different label combinations.

Query: `sum(rate(prometheus_http_requests_total[5m]))`

**5. Label Filtering**

Filters metrics based on label values.

Queries:

- `prometheus_http_requests_total{code="200"}`
- `prometheus_http_requests_total{code!="200"}`

**6. Arithmetic Operations**

Converts memory usage from bytes into megabytes.

Query: `process_resident_memory_bytes / 1024 / 1024`

**7. Top-K Function**

Returns the top five matching time series.

Query: `topk(5, prometheus_http_requests_total)`

### Challenge – Non-200 HTTP Request Rate

Query:

`rate(prometheus_http_requests_total{code!="200"}[5m])`

This calculates the per-second rate of HTTP requests with status codes other than 200 over the last five minutes.

## Task 6 – Prometheus Data Retention and Storage

Prometheus stores collected metrics in its built-in Time Series Database (TSDB).

### Data Retention

Prometheus uses a default data retention period of 15 days.

Retention can be configured using:

- `--storage.tsdb.retention.time=30d`
- `--storage.tsdb.retention.size=1GB`

These settings control how long data is retained and the maximum storage size.

### Checking Storage Usage

Docker can be used to inspect Prometheus storage consumption.

Command: `docker exec prometheus du -sh /prometheus`

### Why Is Persistent Storage Important?

Docker volumes ensure that Prometheus data survives container recreation and restart.

Without persistent storage, collected metrics may be lost when the container is removed.

### What Happens When Retention Is Exceeded?

Prometheus automatically removes older time-series data according to its configured retention limits.

This helps prevent unlimited storage growth and keeps disk usage manageable.
